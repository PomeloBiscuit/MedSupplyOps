Medical supply requisition and inventory management system

An internal system for a fictional hospital: a nursing station submits a requisition, the central storeroom approves it and issues lots by first expiry, first out (FEFO). Every step is written to an append-only audit trail.

This portfolio asks a question beyond which technologies were used: How do you know it is correct?

01 — Why feature count is not the point

The most dangerous errors in this system do not crash it

They raise no error, the screen looks normal, and simply running the app catches none of them:

If this is implemented incorrectlyWhat the user sees
The issue order by expiry date is reversedThe quantity is right, inventory is deducted correctly, and the page looks normal — but the wrong lot was issued
The expiry rule is off by one day (< becomes <=)Each lot loses one usable day. No one reports it
Two people request the last box at the same timeBoth requisitions succeed and inventory becomes -5
An invalid requisition state transition is silently ignoredThe user clicks Approve, sees no error, and the requisition stays in its previous state
The ER diagram drifts from the real schemaThe diagram looks polished, but it is wrong

So the focus of this project is designing a check that distinguishes correct from incorrect behavior for each such rule.

Six gates, all run on every commit

dotnet build   MedSupplyOps.slnx     # Compile and analyze (warnings are errors)
dotnet test    MedSupplyOps.slnx     # 334 tests
dotnet format  --verify-no-changes   # Formatting and naming
scripts/mutation-probe.ps1           # Prove the tests detect incorrect behavior
scripts/generate-er-diagram.ps1 -Check   # Detect ER diagram drift
scripts/check-db-clean.ps1           # Tests must leave no database residue

The first three are common; the last three are the focus of this project.

02 — Mutation probes

Proving the tests can detect the failure

A check that cannot distinguish before from after a fix is no check at all.

All tests passing means only that none failed; it does not mean they can detect the claimed fault. A script therefore deliberately breaks the implementation 13 times, checks that the relevant tests fail each time, then restores the code and checks that the baseline passes again:

ProbeRuleFailing tests
P1 Reverse FEFO order (issue the latest-expiring lot first)First expiry, first out2
P2 Change expiry comparison < to <=A lot remains usable on its expiry date2
P3 Remove the lot-number tie breaker for equal expiry datesDeterministic allocation across environments1
P4 Allow partial issueInsufficient stock fails the entire issue4
P5 Add an illegal state-machine transitionIllegal transitions must be rejected2
P6 Stop requiring a reason for rejectionRejection requires a reason1
P7 Remove SELECT … FOR UPDATE from issueConcurrent requests must not overissue3
P8 Remove query-service DI registrationProduction composition must be complete9
P9 Skip failed lines and continue issuing the restIssue the whole requisition atomically6
P10 Remove the item-row lock during receivingReceiving a new lot for the same item must be serialized2

P12 Give a roleless account unrestricted home-page scopeRoleless accounts must not see hospital-wide data1
P13 Skip an unknown GS1 application identifierReject the entire input rather than accepting part of it1

Another 5 database-level probes try to write invalid data and verify that constraints reject it: negative inventory, an unknown state, a rejected requisition without a reason, and a duplicate item number. The fifth verifies that reusing an item number after soft deletion is allowed. The first four show that invalid data is blocked; only the last shows that valid data is not blocked by mistake.

A real defect found by a probe. A test named for determinism remained green after a probe removed the entire sort key it supposedly checked. Its test data happened to produce the same answer under both sort orders. The test had never checked its claimed rule, and reading the test code alone did not reveal that.

03 — Architecture

Three layers, with separate write and read paths

flowchart TB subgraph web["MedSupplyOps.Web (MVC + Web API + FHIR)"] C["Controllers / Razor Views"] A["Authorization: deny by default + Policy"] end subgraph infra["MedSupplyOps.Infrastructure"] Q["Queries (Dapper handwritten Oracle SQL)"] S["Services: issue / receiving + concurrency control"] P["Persistence (EF Core) write path"] end subgraph domain["MedSupplyOps.Domain (no package dependencies)"] F["FefoAllocator (pure function)"] M["RequisitionStateMachine"] end DB[("Oracle 26ai Free: handwritten DDL + CHECK constraints")] C --> A A --> Q A --> S S --> F S --> P P --> DB Q --> DB
DecisionReason
The Domain layer has no package dependencies (not even EF Core) This is not architectural purity for its own sake: FEFO and inventory rules can be tested without a database, proving they do not depend on persistence details
EF Core for writes, handwritten Oracle SQL for reads If everything were left to the ORM, the author could not explain who generated the SQL, why it looks that way, or how to tune it
Authorization denies by default (fallback policy), with an allowlist of public endpoints With public access as the default, an unmarked endpoint would go unnoticed — and only a signed-out user would discover it
TreatWarningsAsErrors C# has no separate type-checking step. Promoting analyzer warnings to errors gives the third gate something real to block

04 — Database

Conceptual model and actual structure

Conceptual model (Chen notation)

Rectangles denote entities, diamonds denote relationships, and ovals denote attributes; underlined attribute names are primary keys. Double lines between entities and relationships indicate total participation, single lines indicate partial participation, and 1, N, and M indicate cardinality.

Every requisition must come from a department, so the requisition side has a double line. A department can submit none, so its side has a single line.

Allocation is an M:N relationship: one line can draw from several lots to meet its quantity by earliest expiry; one lot can also supply several lines. Allocated quantity describes how many units that line takes from that lot, so it belongs to the relationship itself.

The conceptual relationships “stored at” and “leaves” are valid, but the physical design deliberately omits foreign keys: a lot matches a storage location by name, and audit records preserve the operator as text. These two relationships therefore have no arrows in the relational schema below.

Full system

IDENTITY_USER_CLAIMS, IDENTITY_USER_LOGINS, IDENTITY_USER_TOKENS, and IDENTITY_ROLE_CLAIMS are standard Identity tables unused by this system, so they are omitted from the relational schema.

Three Oracle-specific decisions

Use VARCHAR2(n CHAR) for every string Under AL32UTF8, a Chinese character takes 3 bytes. Default BYTE semantics let VARCHAR2(50) hold only 16 Chinese characters. A long department name triggers ORA-12899; a developer sees a length of 50 and an input of 20 characters, with no obvious explanation.
Function-based index for soft deletion Uniqueness applies only to records not deleted. A direct UNIQUE constraint on item number would prevent reuse after soft deletion, with no message explaining why.
No ON DELETE CASCADE anywhere in the schema Deleting a department and cascading through its requisitions and issue records would destroy the audit trail in a medical setting. All deletion is soft deletion.

05 — Core workflow

Issue: FEFO lot allocation and concurrency control

sequenceDiagram autonumber participant K as Inventory clerk participant W as Web (deny by default) participant S as StockIssueService participant D as Oracle K->>W: Click Issue on an approved requisition W->>S: IssueRequisitionAsync (one transaction) S->>D: SELECT ... FOR UPDATE WAIT 5 (lock by ascending item_id) Note over S,D: Fixed lock order prevents deadlocks S->>S: FefoAllocator: earliest expiry first, lot number breaks ties alt Any line has insufficient quantity S->>D: ROLLBACK S-->>W: Entire requisition fails (no partial issue) else All lines have enough S->>D: UPDATE lot quantity + INSERT allocation + INSERT audit S->>D: COMMIT S-->>W: Success, return the allocated lots end
Why pessimistic rather than optimistic locking Issue is a short, high-contention transaction. To the user, the result is whether stock can be issued. Optimistic locking makes the second person finish all the work before being told to retry; pessimistic locking makes them wait at the read. They then see the actual inventory after the first deduction and receive a meaningful message such as “insufficient stock; 1 available.”
Lock timeout is not insufficient stock A timeout means stock may exist but the lock was unavailable, so the caller should retry. Treating it as shortage creates a false out-of-stock message. On timeout, available quantity is returned as -1 rather than 0: no data was read, and returning 0 would imply it was checked and found empty.
Database CHECK (quantity >= 0) is the final defense After probe P7 removes the application lock, inventory still cannot become negative: the second UPDATE violates CHECK and fails. The application gives correct, helpful results; the database guarantees the data remains valid.

Requisition state machine

Six states and five legal transitions. An illegal transition must be rejected with an explicit error, never silently ignored — probe P5 checks this.

06 — Performance

Logical reads instead of execution time

Timing measures “your query + operating system scheduling + GC + other processes” when only the first matters. The measurement therefore uses Buffers (logical reads) from DBMS_XPLAN and requires the same A-Rows before and after. If the returned row count changes, the query has changed rather than improved.

QueryBefore indexAfter indexA-Rows
FEFO available-lot query1004 buffers (full table scan)111 buffers (index range scan)101 → 101
Home audit list (20 groups of ten thousand audit rows)2006 buffers54 buffers (−97%)5 → 5
Expired lots still in stock (2 groups of ten thousand lots)19 buffers; an existing index is used — no new index needed1 → 1
The last row is deliberate: “no new index needed” is also a conclusion. Adding an unnecessary index to make numbers look better is as dishonest as shrinking the query to improve them.

07 — Operations

The safety net must also be verified

AreaWhat was done
Backup and restore drill Two backup layers (Data Pump logical backup + cold volume backup). A drill found that the script left two files of plausible size even though they were not valid backups: the container had been SIGKILLed rather than shut down cleanly. Packaging now requires a clean-shutdown marker and an exit code other than 137; failures write UNTRUSTED.txt. Restore also fixed a false failure by checking the log inside the container. A destructive restore drill then confirmed that marker data written before restore disappeared and four table row counts returned to baseline.
Cold-start replay From a clean clone and a fresh database volume, all six gates were rerun using the README instructions. This exposed a test that failed only on a fresh database but remained green in an accumulated environment.
Requirements traceability gate Each requirement ID appears exactly once in the traceability table. For a row marked implemented, its test method, probe ID, and file path must exist. Partially implemented work cannot be marked implemented. This gate runs with the tests rather than as a separate, easily forgotten step.
Tests must leave no residue Integration tests share one Oracle container. Residual data escapes individual assertions because each test checks only its own scope. A separate gate therefore requires the database to contain only seed data after the test run.

08 — Scope

Deliberate exclusions

The requirements explain the boundaries: no patient records, medical orders, registration, or insurance claims; no external purchasing and acceptance, transfers between hospitals, front-end SPA, or high-availability cluster.

This is deliberate: the system handles no patient data. Without clinical domain knowledge, it does not pretend to have it. An honest inventory system is better than a seemingly complete “hospital system” with an incorrect model.
